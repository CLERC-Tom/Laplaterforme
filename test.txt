                        EXERCICE 1 — PACKET TRACER
================================================================================

Lien GitHub (dossier) :
  https://github.com/clerctom/Laplaterforme/tree/main/Exercice_1

------------------------------------------------------------------------
PROCESS
------------------------------------------------------------------------

Topologie :
  Réseau de 3 bureaux identiques, chacun composé d'un switch, d'un point
  d'accès Wi-Fi, de 2 PC fixes, d'un PC portable et d'un téléphone IP.
  Un routeur Cisco 1941 centralise le routage et le DHCP.

1. Création des VLANs
   Quatre VLANs ont été définis pour segmenter le trafic :
     - VLAN 1  (VoIP)            -> 192.168.0.0/24
     - VLAN 10 (PC fixes)        -> 192.168.10.0/24
     - VLAN 20 (Wi-Fi)           -> 192.168.20.0/24
     - VLAN 30 (Administration)  -> 192.168.30.0/24

2. Configuration des switches (x3)
   Chaque switch est configuré de manière identique :
     - Fa0/1  : TRUNK vers le routeur (uplink principal)
     - Fa1/1, Fa2/1  : ACCESS VLAN 1 (téléphones IP)
     - Fa3/1, Fa4/1  : ACCESS VLAN 20 (points d'accès Wi-Fi)
     - Fa5/1, Fa6/1  : ACCESS VLAN 10 (PC fixes)
     - Fa7/1         : ACCESS VLAN 30 (administration)
     - Fa8/1         : TRUNK vers uplink / switch suivant

3. Configuration du trunk
   Le lien entre chaque switch et le routeur est configuré en mode trunk
   (802.1Q), ce qui permet de transporter tous les VLANs sur un seul
   câble physique.

4. Routage inter-VLAN (Router-on-a-stick)
   Le routeur 1941 utilise des sous-interfaces sur G0/0 pour router entre
   les VLANs sans câble supplémentaire :
     - G0/0.1  (native) -> 192.168.0.1/24
     - G0/0.10          -> 192.168.10.1/24
     - G0/0.20          -> 192.168.20.1/24
     - G0/0.30          -> 192.168.30.1/24

5. Configuration DHCP
   Un pool DHCP est créé par VLAN directement sur le routeur.
   Les adresses .1 à .9 sont exclues (passerelles + éventuels statiques).
   Les baux DHCP démarrent donc à .10 pour chaque réseau.

6. Wi-Fi
   Les points d'accès sont branchés sur les ports ACCESS VLAN 20.
   Les PC portables se connectent via ces AP et obtiennent une IP en
   DHCP sur le réseau 192.168.20.0/24.

                       EXERCICE 2 — ACTIVE DIRECTORY
================================================================================

Lien GitHub (dossier) :
  https://github.com/clerctom/Laplaterforme/tree/main/Exercice_2

------------------------------------------------------------------------
PROCESS
------------------------------------------------------------------------

Environnement :
  Travaillant sur macOS, j'ai déployé un hyperviseur Proxmox VE sur une
  machine physique, sur lequel j'ai créé une VM Windows Server 2022.
  Le domaine Active Directory créé s'appelle "laplateforme.io".

1. Installation d'Active Directory (script 01_install_AD.ps1)
   - Installation du rôle AD DS via PowerShell :
       Install-WindowsFeature -Name AD-Domain-Services -IncludeManagementTools
   - Promotion du serveur en contrôleur de domaine via Install-ADDSForest
     avec le domaine "laplateforme.io" et le NetBIOS "LAPLATEFORME".
   - Le serveur redémarre automatiquement après la promotion.

2. Peuplement de l'AD (script 02_populate_AD.ps1 + users.csv)
   - Création de l'arborescence OU :
       LaPlateforme (OU racine)
         |-- Utilisateurs
         |-- Groupes
   - Lecture du fichier users.csv (prénom, nom, groupe1..groupe6) pour
     créer automatiquement tous les groupes de sécurité manquants.
   - Création de chaque utilisateur avec :
       * SamAccountName au format "p.nom" (initiale prénom + point + nom)
       * Mot de passe initial forcé : "Azerty_2025!"
       * ChangePasswordAtLogon = $true -> l'utilisateur est contraint de
         changer son mot de passe à la première connexion
   - Affectation automatique de chaque utilisateur à ses groupes (jusqu'à
     6 groupes par ligne du CSV).

                        EXERCICE 3 — DOCKER / WORDPRESS
================================================================================

Lien GitHub (dossier) :
  https://github.com/clerctom/Laplaterforme/tree/main/Exercice_3

------------------------------------------------------------------------
PROCESS
------------------------------------------------------------------------

Objectif :
  Déployer WordPress en isolant chaque rôle dans un container dédié,
  reliés entre eux via un réseau Docker interne et des volumes partagés.

Architecture (3 containers) :
  +----------+       FastCGI        +---------+       SQL        +---------+
  |  nginx   | ------------------> |   php   | --------------> | mariadb |
  | :80      |   (port 9000)       | fpm8.3  |                 | latest  |
  +----------+                     +---------+                  +---------+
       |                                |
       +--------------------------------+
              Volume partagé : wp_data (/var/www/html)

Détail des containers :
  - nginx (nginx:alpine)
      Reçoit les requêtes HTTP sur le port 80.
      Sert les fichiers statiques directement depuis le volume partagé.
      Délègue les fichiers .php au container "php" via FastCGI (port 9000).
      La directive try_files gère les URLs propres de WordPress.

  - php (wordpress:php8.3-fpm)
      Exécute le code PHP de WordPress via PHP-FPM.
      Se connecte à "mariadb" pour lire/écrire les données.
      Partage le volume wp_data avec nginx -> les deux containers voient
      exactement les mêmes fichiers WordPress.

  - mariadb (mariadb:latest)
      Base de données SQL de WordPress.
      Stocke articles, utilisateurs, paramètres dans le volume db_data.

Volumes persistants :
  - wp_data (39,9 MB) : monté dans nginx ET php sur /var/www/html
      -> volume commun qui permet à nginx de servir les statics et à
         php d'exécuter le code sans copie entre containers.
  - db_data : monté dans mariadb sur /var/lib/mysql
      -> données SQL persistantes même après suppression des containers.

Ordre de démarrage (depends_on) :
  mariadb  ->  php  ->  nginx

Lancement :
  cd Exercice_3/Files
  docker compose up -d

WordPress est ensuite accessible sur http://localhost.
